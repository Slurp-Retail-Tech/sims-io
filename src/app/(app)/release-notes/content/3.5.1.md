title: "Respond.io ticket creation no longer holds two database connections"
summary: "When a Respond.io webhook created a ticket, the merchant-name lookup reached for a second database connection while the first was still mid-transaction. Under load that could stall requests indefinitely, because callers waiting for a connection wait without a timeout."
fixed:
  - title: "Merchant name lookup uses the connection it was given"
    detail: "Creating a ticket from a Respond.io contact-tag event runs as a single transaction. The merchant and outlet name lookup inside it was still going through the shared connection pool, checking out a second connection while the transaction held the first. With ten connections available and no queue timeout, enough concurrent webhooks could exhaust the pool and leave every waiting request hanging. The lookup now runs on the transaction's own connection, which also means it reads a consistent snapshot. The two other places that call it are unaffected."
