title: "Renewal link API and CommercePay sessions"
summary: "The token-gated API behind the merchant's renewal link is in place: read the invoice, switch the term, download the document, and open a CommercePay payment session."
new:
  - title: "Public renewal API"
    detail: "Four token-gated endpoints under /api/public/renewal/{token}: the invoice as the merchant sees it, a term switch, the PDF, and Pay. Each is rate-limited twice over, by caller address and by a hash of the token, and a malformed token is refused before any database work. Staff visits are recognised and never counted as merchant opens."
  - title: "Term switching"
    detail: "Switching between one year and six months reprices every line through the same rules the nightly run used. A term is offered only when every outlet on the invoice can be priced on it; a line with a one-off price pins the invoice to its current term; a switch that would need a price review is refused rather than granted quietly. The stored PDF is re-rendered after a switch."
  - title: "CommercePay payment sessions"
    detail: "Pay captures the receipt email and opens a hosted session at the gateway. Each attempt is its own numbered session with a unique reference, allocated under a lock so two clicks cannot collide. A live session for the same amount and term is resumed rather than replaced. Nothing here marks an invoice paid; that arrives with the signed callback in the next release."
  - title: "Payment status vocabulary"
    detail: "The gateway's eighteen status codes are mapped to the handful of outcomes SIMS acts on. Only code 1 is paid. An authorisation is not a payment. Every refund code lands on a person."
improved:
  - title: "One Redis connection"
    detail: "The rate limiter and the gateway token cache now share a single client instead of each opening their own."
