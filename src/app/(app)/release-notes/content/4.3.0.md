---
version: "4.3.0"
date: "2026-08-29"
title: "Server logs are now structured and traceable"
summary: "Server-side logging was free-form text with no way to tie a message to the request that caused it. Logs are now machine-readable in production, carry a request identifier, and hide anything credential-shaped."
new:
  - title: "Structured logging with a request identifier"
    detail: "Each server-side event is now a single machine-readable line in production carrying a timestamp, severity, scope, message and any structured detail, so logs can be searched and filtered rather than read. Local development keeps the short readable format. Where a route opts in, everything it triggers shares one request identifier, so a single failure can be followed across all the messages it produced."
  - title: "A request identifier you can quote"
    detail: "Requests to routes that have opted in return an identifier in the response, and failures include it in the error body. Someone reporting a problem can pass that identifier along, and it maps directly to the log lines for their request. An identifier supplied by an upstream proxy is honoured so a trace started there continues here."
improved:
  - title: "Credentials are kept out of log output"
    detail: "Structured detail attached to a log entry has anything whose name looks like a password, token, secret, cookie or key replaced before it is written. The name is kept so it is clear a value was present and withheld."
  - title: "Error details are recorded consistently"
    detail: "Errors now record their type, message, stack and system error code as separate fields, so failures like a refused connection can be filtered on directly instead of matched by text."
fixed:
  - title: "An upstream request identifier can no longer forge log entries"
    detail: "The identifier is accepted from an incoming request header, which is outside our control. It is now only honoured when short and plainly formatted; anything else is replaced with a freshly generated one. Without that, a crafted value containing a line break could have inserted convincing fake entries into the log."
