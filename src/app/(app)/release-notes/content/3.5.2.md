version: "3.5.2"
date: "2026-08-29"
title: "Respond.io ticket updates are now all-or-nothing"
summary: "Every Respond.io webhook that changes a ticket now writes the change and its history entry as one unit, and a status update that loses a race no longer records a change that never happened."
fixed:
  - title: "A ticket can no longer move to In Progress without it really happening"
    detail: "When an agent's first reply moved a ticket to In Progress, the update itself was guarded against a race but the history entry was not. If someone else changed the ticket's status at the same moment, the update correctly did nothing while the history still recorded the move — leaving an audit trail that claimed a transition that never occurred. The status is now re-checked under a lock and the handler stops before writing anything if the ticket has already moved on."
  - title: "Ticket changes and their history entries commit together"
    detail: "Setting the merchant success PIC, moving a ticket to In Progress, closing a ticket, and creating a ticket from a contact tag each wrote the ticket row and its history entry as two separate statements on two different database connections. An interruption between them left a changed ticket with no record of the change. Each is now a single transaction."
  - title: "Closing a ticket records the status it actually replaced"
    detail: "The history entry for a Respond.io close previously recorded no previous status. It now reads the current status under the same lock that performs the close, so the entry reflects what was really replaced."
  - title: "Two simultaneous Respond.io events can no longer open duplicate tickets"
    detail: "Creating a ticket from a contact tag checked for an existing open ticket and then inserted, without holding anything between the two steps. Two distinct events arriving together could both pass the check and both create a ticket. The check and the insert now run inside one transaction, serialised per contact."
