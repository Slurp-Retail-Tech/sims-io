version: "4.2.0"
date: "2026-08-29"
title: "The container health check now reflects reality"
summary: "The deployment health check reported the application healthy as long as the process accepted a connection — including with the database, cache and file storage all unreachable. It now checks the dependencies it actually needs."
new:
  - title: "Two health endpoints, for two different questions"
    detail: "A liveness endpoint answers whether the process itself is up, doing no other work so it cannot fail because something else is down. A readiness endpoint checks the database, the cache and file storage in parallel, each with its own two second budget, and reports the status and response time of each. Keeping them separate means a database outage is never mistaken for a stuck process that needs restarting."
fixed:
  - title: "A container with everything down no longer reports healthy"
    detail: "The health check requested the application's home page, which redirects unauthenticated visitors to the login screen — and the check treated that redirect as success. It therefore passed whenever the process was listening, regardless of whether the database was reachable, so orchestration could never detect an outage or replace a broken container. It now requests the readiness endpoint, which fails when the database is unreachable."
  - title: "Lost file storage no longer comes back silently empty"
    detail: "When the storage bucket could not be found, the application created a new empty one. That is convenient locally but hides the worst case in production: if a storage volume were lost, an empty bucket would be recreated and the loss would only surface later, when someone opened an attachment and found it missing. In production this now fails loudly instead. Local development is unchanged."
improved:
  - title: "Only the database failing takes a container out of service"
    detail: "The cache or file storage being unavailable reports as degraded rather than unhealthy. The application still serves most traffic without them, so removing the container from the load balancer in that situation would turn a partial problem into a full outage. Their status is still visible in the readiness response."
  - title: "Local storage container reports its own health"
    detail: "The local development file storage service now has a health check, so it can be waited on like the database."
