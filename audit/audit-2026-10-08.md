# Merchant Import Audit — 2026-10-08

## Scope

| Layer | File |
|---|---|
| Trigger | `src/app/api/merchants/import/route.ts` |
| Status | `src/app/api/merchants/import/status/route.ts` |
| Job handler | `src/lib/job-handlers/merchant-import.ts` |
| Cursor | `src/lib/merchant-import-cursor.ts` |
| Page importer | `src/lib/merchant-import.ts` |
| POS client | `src/lib/pos-api.ts` |
| Runner | `src/lib/job-runner.ts`, `src/lib/job-tick.ts`, `src/lib/job-runner-core.ts` |
| UI | `src/app/(app)/merchants/page.tsx` (import button + status poll) |
| Schema | `merchants`, `merchant_outlets`, `merchant_import_runs` in `schema.sql` / `migrations/003_prod_schema_alignment.sql` |

How it works: `POST /api/merchants/import` (Admin + `/merchants`, or `x-cron-secret`) adds a singleton `merchant-import` job and runs one 45 s slice inline. The cron tick runs the remaining slices. Each slice logs in to POS, then fetches 100-merchant pages from `franchise-retrieve` and upserts each merchant, then each of its outlets. After every page it saves a page cursor.

## What's already solid

- Single-flight is enforced twice: a `UNIQUE (job_type, dedupe_key)` key plus a MySQL `GET_LOCK`. Two imports cannot interleave.
- Every write is a parameterised upsert, so there's no SQL injection, and replaying a page after a resume is safe.
- The cron secret is compared in constant time. A manual import needs the Admin role.
- Every POS call has a timeout (30 s per data call, 10 s for login), login is never retried, and logged URLs are stripped of their query string.
- `MERCHANT_IMPORT_MAX_PAGES` caps the page loop, and hitting the cap is reported as a failure rather than a success.

## Detailed Findings

### MI-01 — High: One malformed POS record stops every future import at the same page

**What happens.** Each record goes straight into a column with a length limit: `external_id VARCHAR(120)`, `name VARCHAR(255)`, `fid VARCHAR(120)`, `status VARCHAR(60)`, and the same on `merchant_outlets`. Nothing checks length or type first. `src/lib/db.ts` doesn't change `sql_mode`, so MySQL 8's default `STRICT_TRANS_TABLES` is on. An over-long value throws `ER_DATA_TOO_LONG` instead of being truncated. The `as string` casts don't check anything at runtime either. If a field comes back as an object, mysql2 turns it into `` `key` = 'val' `` and the statement fails.

**Why it's High.** Nothing catches the error per record, so the whole slice throws:

1. The cursor stays at the last good page. The reaper puts the run back in the queue, and it fails on the same page each time until `max_attempts` (5). Then it's marked `failed`.
2. The next scheduled import starts a new job at **page 1** and dies at the same record.
3. Every merchant after that record is never refreshed again. MI-03 hides the cause, so nobody gets told.

**Fix.**
- Normalise each record before writing it. Make scalars into strings, cut `name`/`status` to the column length, and skip records whose `external_id` is empty or over 120 characters.
- Wrap each merchant's writes in `try/catch`. Count failures in `progress.failed` and record them through `checkpoint({ items })` → `job_run_items` (the per-unit log the runner already has). Then keep going.
- Fail the run only when the failure rate is above a threshold. Don't fail it on the first bad record.

### MI-02 — Medium: Unrecognised payloads and capped page sizes are reported as a successful import

**Unrecognised payload.** `getPosApiItems` returns `[]` for any shape it doesn't recognise. That includes a `200` that carries `{ "message": "Unauthenticated" }` or a renamed envelope key. The handler takes that as reason `"empty"` and marks the run **succeeded** with 0 records.

**Capped page size.** The loop stops on `itemsReturned < perPage`. If POS quietly limits `per_page` to something below 100 (many Laravel-style APIs cap at 50), page 1 comes back short. The import stops after one page and still reports success.

**Fix.**
- Have `getPosApiItems` (or a sibling function) tell apart "no array found" from "empty array". Throw on the first case.
- If the payload has pagination metadata (`last_page`, `next_page_url`, `meta.total`), stop based on that instead of guessing from page length.
- Sanity check: if page 1 is empty but `merchants` already has rows, fail the run instead of reporting success.

### MI-03 — Medium: The real failure reason is never saved; the UI shows "Abandoned … lease expired"

When the handler throws, `driveJobType` logs the error and rethrows it. Nothing writes it to `job_runs`. The reaper then sets `error_message` to `Lease expired on attempt N.`, and finally to `Abandoned after 5 attempt(s); lease expired.`. That's the only text the status route and UI ever show. The cause ("Import failed with status 500", "Data too long for column 'name'") exists only in server logs.

A second problem: the slice run inside `POST /api/merchants/import` can throw. The route then returns 500 "Import failed", but the job **is** still queued and will be retried. The user is told it failed when it's actually still running.

**Fix.**
- In the `catch` in `driveJobType`, write a cleaned-up, length-capped `error_message`, guarded by `lease_owner = ?`, before rethrowing.
- Change the reaper's `CONCAT` to keep that message (for example `CONCAT(COALESCE(error_message,''), ' — lease expired …')`).
- In the route, return 202 with `slice: { error: true }` when the job was queued but the inline slice threw.

### MI-04 — Medium: A single page can take longer than its lease, wasting retry attempts

`hasBudget` only runs *before* a page starts. After that the page runs to the end. The worst case for one page's network calls:

| Step | Time |
|---|---|
| Header-auth fetch | 30 s |
| Query-token retry on 401 | 30 s |
| Re-login | 10 s |
| Header-auth fetch with new token | 30 s |
| Query-token retry | 30 s |

That's ≈130 s, plus up to roughly 1,000 serial upserts (MI-09). The lease is 75 s (45 s budget + 30 s margin) and is only renewed at a checkpoint.

When a page runs past the lease, a tick in another process calls `expireStaleLeases` and puts the run back in the queue. The original worker's checkpoint then fails and `yieldJobRun` does nothing. The page is replayed, and `attempt` has already gone up by one, so a slow POS alone can use up all 5 attempts. `GET_LOCK` still stops two workers running at once, so the damage is lost attempts and replayed work, not data corruption.

**Fix.**
- Check the budget per merchant inside the page and save a cursor partway through (page + offset), or use smaller pages.
- Or renew the lease (`checkpoint`) once the fetch returns and before the writes start.
- Make the 401 path take less time, for example by making the query-token fallback and the re-login mutually exclusive.

### MI-05 — Medium: The full upstream error body is copied into the error message, which can leak the token

```ts
const errorBody = await response.text().catch(() => "")
throw new Error(`Import failed with status ${response.status}${details}`)
```

The whole body goes into the error with no size limit, and it ends up in logs. In the legacy path it also went into `merchant_import_runs.error_message`, which the status route returns. Here's how that leaks a credential:

1. A first 401 makes `fetchPosApiWithTokenFallback` retry with `?api_token=<token>&token=<token>`.
2. If that retry fails with an error page that repeats the request URL (Laravel/Symfony debug pages do), the live token is now in the error text.
3. That skips the `redactUrlForLogs` guard the module was designed around.

**Fix.**
- Cap the body at about 500 characters.
- Remove the current token from it (`body.replaceAll(session.token, "[redacted]")`).
- Or leave the body out completely when the response came from the fallback request.

### MI-06 — Medium: Merchants and outlets removed or moved upstream are never reconciled

The importer only ever upserts. That causes three problems:

- **Removed upstream:** a merchant or outlet deleted in POS stays in SIMS forever, with its last known `status`. It keeps showing on maps (`/api/maps/outlets`), in renewals (`/api/renewals/expiring`), in the ticket outlet picker, and in exports.
- **Moved to another merchant:** an outlet that moves to a different merchant gets a **second** row, because the unique key is `(merchant_external_id, external_id)`. The old row stays attached to the previous merchant. The `merchant_external_id = VALUES(...)` line in `ON DUPLICATE KEY UPDATE` does nothing, because that column is part of the key the row was matched on.
- **Feed changes mid-run:** offset paging over a feed that changes during a run skips records without any sign. A run can span many cron ticks, so the window for this is wide.

**Fix.**
- Add a `last_seen_job_run_id` column to both tables (a migration, plus an update to `schema.sql`) and set it on every upsert.
- Only after a run **succeeds**, mark rows not seen in that run as removed (soft flag, not delete). Exclude them from the downstream queries.
- Decide whether an outlet's identity should be `external_id` alone. If OIDs are globally unique, change the unique key and turn the move into an update.

### MI-07 — Medium: Records without an ID fall back to the name as identity, so same-name merchants merge

`getExternalId` tries `id → fid → franchise_id → code → name`, and the name falls back to `"Unknown Merchant"`. So:

- Two different merchants with no ID and the same name collapse into one row.
- Every record with no ID and no name lands on a single `external_id = "Unknown Merchant"` row.
- If a later feed does include the `id`, a duplicate row is created and the name-keyed one is left stale.

**Fix.** Treat a record with no stable ID as a skipped unit: count it and log it, but don't write it.

### MI-08 — Low: Token goes out five ways, and the custom headers still travel on a cross-origin redirect

Every POS data call sends the token as `Authorization: Bearer`, `X-Api-Token` and `X-Api-Key`. After a 401 it also sends `Authorization: Token` and two query parameters.

On a cross-origin redirect, fetch drops `Authorization` and `Cookie`. It keeps custom headers like `X-Api-*`, and it keeps the query string. A misconfigured `POS_IMPORT_URL`, or a redirect on the POS side, would send the token to wherever the redirect points.

**Fix.**
- Pass `redirect: "error"` (or `"manual"` and allow same-origin only) on POS data calls.
- Confirm with the POS team which single auth scheme `franchise-retrieve` accepts, and drop the rest.

### MI-09 — Low: Writes are serial, one per merchant and one per outlet (1 + outlets per merchant)

One page costs `100 × (1 + outlets)` serial round trips through the pool. With ~10 outlets per merchant that's about 1,100 queries per page. This is the main reason a page can outlive its lease (MI-04).

**Fix.** Build one multi-row `INSERT … ON DUPLICATE KEY UPDATE` for the page's merchants and one for its outlets, inside a single transaction.

### MI-10 — Low: Numeric-string outlet counts become 0; ID fields are picked inconsistently

- `getOutletCount` uses `Number.isFinite(value)`, which doesn't convert strings. So `outlet_count: "5"` is stored as `0`. Use `Number(value)`, then check it.
- `getExternalId` picks the ID with `??`, but the `fid` field uses `||`. If `id` is `0` or `""`, the two pick different source fields. Use one shared helper for both.

### MI-11 — Low: Progress counters reset every slice; skipped outlets are never counted

`readProgress(null)` throws away the saved `progress_json` at the start of every slice. As a result `updated` and `currentLabel` only reflect the current slice; `processed` is unaffected because it's rebuilt from the cursor. Outlets skipped for having no ID (`continue` at line 234) aren't counted anywhere.

**Fix.** Read the previous progress from the claim. Increment `progress.skipped` for skipped outlets.

### MI-12 — Low: Status route only checks that the user is logged in and returns raw error text

`GET /api/merchants/import/status` only calls `requireAuthenticatedUser`, so any logged-in user can read it whatever their page access. It returns `error_message` unchanged, which combined with MI-05 can include upstream response text.

**Fix.** Gate it like the trigger route (`resolveApiUser` with `allowedPaths: ["/merchants"]`) and return the cleaned-up message from MI-03.

### MI-13 — Low: Old `runMerchantImport` is dead code

Nothing calls `runMerchantImport`. It still has the problems the job runner was built to fix: no page cap, an `UPDATE` that runs twice, a fake `items = { length }` object, and it writes to the old `merchant_import_runs` table.

**Fix.** Delete it. Once every environment has a `job_runs` import on record, remove the old-table fallback in the status route too.

### MI-14 — Low: The field mapping has no tests

Only `merchant-import-cursor.ts` has tests. The mapping functions (`getExternalId`, `getStatus`, `getOutletCount`, `getOutlets`) are private and live in a module that imports `@/lib/db`, so `node --test` can't load them. That's why MI-07 and MI-10 went unnoticed.

**Fix.**
- Move the mapping into a pure module, `src/lib/merchant-import-mapping.ts`, with a colocated `.test.ts`.
- Cover: the ID fallback order, numeric and string statuses, the outlet shapes (array / object / count), over-long fields (MI-01), and unrecognised payload envelopes (MI-02).

## Suggested order of work

1. **MI-01 + MI-03 + MI-05:** handle errors per record, save the real error, and limit/clean up the error body. Together these stop silent, permanent import failures.
2. **MI-02 + MI-14:** move the mapping into a pure module with tests, and catch unrecognised payloads.
3. **MI-04 + MI-09:** batch writes and check the budget per merchant.
4. **MI-06 + MI-07:** reconciliation. Needs a migration, so update `schema.sql` and `docs/TDD.md` in the same change.
5. Clean up the rest (MI-08, MI-10 to MI-13).
